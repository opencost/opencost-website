## AWS Configuration

### Cost Allocation

OpenCost will automatically read the node information `node.spec.providerID` to determine the cloud service provider (CSP) in use. If it detects the CSP is AWS, it will attempt to pull the AWS on-demand pricing from the configured public API URL with no further configuration required.

OpenCost will request pricing data from the us-east-1 region for your `node_region` using the template:
```sh
https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonEC2/current/${node_region}/index.json
```

The location should be automatically detected, but this URL can be overwritten using the environment variable `AWS_PRICING_URL`.

### AWS Spot Instance Data Feed

AWS [Spot Instance Data Feed](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-data-feeds.html) from the configured S3 bucket
* Set up [Spot Instance Data Feed](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-data-feeds.html).
* Create a role for OpenCost with access to the spot feed bucket. Attach the policy below to the role and replace CHANGE-ME with your spot bucket name.

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Action": [
                "s3:ListAllMyBuckets",
                "s3:ListBucket",
                "s3:HeadBucket",
                "s3:HeadObject",
                "s3:List*",
                "s3:Get*"
            ],
            "Resource": [
                "arn:aws:s3:::CHANGE-ME"
            ],
            "Effect": "Allow",
            "Sid": "SpotDataAccess"
        }
    ]
}
```

#### Configuration

The data feed will provide specific pricing information about any Spot instances in your account on an hourly basis. After setting this up, the bucket information can be provided through options in the AWS provider configuration file.
* `awsSpotDataBucket` - The name of the S3 bucket Spot Instance Data Feed is publishing to.
* `awsSpotDataRegion` - The region configured for Spot Instance Data Feed
* `awsSpotDataPrefix` - The prefix (if any) configured for Spot Instance Data Feed
* `projectID` - The AWS Account ID

Example configuration:

```json
{
    "provider": "aws",
    "description": "AWS Provider Configuration. Provides default values used if instance type or spot information is not found.",
    "CPU": "0.031611",
    "spotCPU": "0.006655",
    "RAM": "0.004237",
    "GPU": "0.95",
    "spotRAM": "0.000892",
    "storage": "0.000138888889",
    "zoneNetworkEgress": "0.01",
    "regionNetworkEgress": "0.01",
    "internetNetworkEgress": "0.143",
    "spotLabel": "kops.k8s.io/instancegroup",
    "spotLabelValue": "spotinstance-nodes",
    "awsSpotDataRegion":"us-east-2",
    "awsSpotDataBucket": "my-spot-bucket",
    "awsSpotDataPrefix": "spot_pricing_prefix",
    "projectID": "012345678901"
}

```

#### Security for AWS integration

OpenCost uses the [AWS SDK for Go](https://aws.amazon.com/sdk-for-go/) to pull Spot data feed information. There are multiple supported ways to [configure security](https://aws.github.io/aws-sdk-go-v2/docs/configuring-sdk/#specifying-credentials).

The recommended setup is to leverage [IAM roles for Service Accounts](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html) or [EKS Pod Identities](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html).

### IAM Roles for Service Accounts

After creating the role and policy, attach the role as an annotation on the service account in your local OpenCost Helm values file:

```yaml
serviceAccount:
  create: true
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/S3Access
```

### EKS Pod Identities

See [AWS Documentation on EKS Pod Identities](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html)

To use EKS Pod Identities with OpenCost:

1. Configure the EKS Pod Identities add on: https://docs.aws.amazon.com/eks/latest/userguide/pod-id-agent-setup.html
2. Create the EKS Pod Identity association: https://docs.aws.amazon.com/eks/latest/userguide/pod-id-association.html
3. Update your local OpenCost Helm values file with:

```yaml
serviceAccount:
  create: true
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/S3Access
  name: name-of-service-account-from-step-2  # can be omitted if the name of the service account is exactly 'opencost'
```

## AWS Cloud Costs

<CloudCostsInfo/>

Cloud Costs reads your AWS [Cost and Usage Report](https://docs.aws.amazon.com/cur/latest/userguide/what-is-cur.html) (CUR) through Amazon Athena. Before configuring OpenCost you need:

1. A CUR delivered to an S3 bucket. Both report versions are supported:
   * **CUR 2.0**, created in *Billing and Cost Management > Data Exports*. This is the recommended format for new setups.
   * **CUR 1.0** (legacy), created in *Billing and Cost Management > Cost and Usage Reports*.
2. An Athena database and table over that bucket. Both export types can provision these for you as part of the export definition.
3. An S3 bucket for Athena query results. Naming it to match `s3://aws-athena-query-results-*` keeps it consistent with the IAM policy below.

### CUR 2.0

OpenCost detects the report version at query time — there is no version setting in the configuration. Detection is based on the presence of any of the CUR 2.0 columns `resource_tags`, `line_item_usage_account_name`, or `bill_payer_account_name` in the Athena table.

Two behaviors change when a CUR 2.0 table is detected:

* **Tags.** CUR 1.0 flattens each tag into its own column (`resource_tags_user_team`). CUR 2.0 stores them in a single `resource_tags` map column, which OpenCost reads with key lookups such as `resource_tags['user_team']`.
* **Partitions.** CUR 1.0 tables are partitioned on `year` and `month`; CUR 2.0 tables are partitioned on `billing_period`.

Because CUR 2.0 lets you exclude any column from the export, leave **`resource_tags` enabled and include resource IDs** when defining the export. Without `resource_tags`, OpenCost falls back to the CUR 1.0 code path, finds no tag columns, and attributes no spend to Kubernetes beyond `AmazonEKS` line items.

### Configuration file

Cloud Costs are configured with a `cloud-integration.json` file containing one or more Athena integrations:

```json
{
  "aws": {
    "athena": [
      {
        "bucket": "<ATHENA_BUCKET_NAME>",
        "region": "<ATHENA_REGION>",
        "database": "<ATHENA_DATABASE>",
        "table": "<ATHENA_TABLE>",
        "workgroup": "<ATHENA_WORKGROUP>",
        "account": "<ACCOUNT_NUMBER>",
        "authorizer": {}
      }
    ]
  }
}
```

* `bucket` is the `s3://` URI of the bucket storing Athena query results, which OpenCost has permission to read and write. The bucket can have a canned ACL set to Private or other permissions as needed.
* `region` is the AWS region Athena is running in.
* `database` is the name of the database created by the Athena setup. For a legacy CUR created by CloudFormation, the database name is available as the value (physical id) of `AWSCURDatabase` in the CloudFormation stack.
* `table` is the name of the table created by the Athena setup. For a legacy CUR, the table name is typically the database name with the leading `athenacurcfn_` removed (but is not available as a CloudFormation stack resource).
* `account` is the AWS Account ID where the Athena CUR is. For example: `530337586277`.
* `authorizer` selects how OpenCost authenticates to AWS. See [Authorization](#authorization) below.

`bucket`, `region`, `database`, `table`, `account`, and `authorizer` are required; a configuration missing any of them is rejected. The remaining fields are optional:

* `workgroup` is the Athena workgroup to run queries in. When omitted, AWS applies its default (`primary`).
* `catalog` is the Athena data catalog. When omitted, AWS applies its default (`AwsDataCatalog`).
* `resultReuseMaxAgeMinutes` enables Athena query result reuse for the given number of minutes. Setting it is worthwhile when many clusters run the same CUR query.

### Authorization

The `authorizer` block accepts one of four `authorizerType` values.

#### IAM Roles for Service Accounts (recommended)

`AWSServiceAccount` uses whatever ambient credentials the pod has — an [IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html) role, an [EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html), or an EC2 instance profile — so no secrets are stored in the configuration file:

```json
{
  "aws": {
    "athena": [
      {
        "bucket": "s3://aws-athena-query-results-my-cur",
        "region": "us-east-1",
        "database": "athenacurcfn_my_cur",
        "table": "my_cur_2_0",
        "workgroup": "primary",
        "account": "123456789012",
        "authorizer": {
          "authorizerType": "AWSServiceAccount"
        }
      }
    ]
  }
}
```

To set this up with IRSA:

1. Register an IAM OIDC provider for your cluster, if you have not already:

   ```sh
   eksctl utils associate-iam-oidc-provider --cluster <CLUSTER_NAME> --approve
   ```

2. Create an IAM role whose trust policy allows the OpenCost ServiceAccount to assume it. Replace `<ACCOUNT_NUMBER>`, `<OIDC_HOST>` (the cluster's OIDC issuer URL without the `https://` prefix), and `<NAMESPACE>`:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Principal": {
           "Federated": "arn:aws:iam::<ACCOUNT_NUMBER>:oidc-provider/<OIDC_HOST>"
         },
         "Action": "sts:AssumeRoleWithWebIdentity",
         "Condition": {
           "StringEquals": {
             "<OIDC_HOST>:sub": "system:serviceaccount:<NAMESPACE>:opencost",
             "<OIDC_HOST>:aud": "sts.amazonaws.com"
           }
         }
       }
     ]
   }
   ```

3. Attach the [Cloud Costs IAM policy](#cloud-costs-iam-policy) below to that role.

4. Annotate the OpenCost ServiceAccount with the role in your local OpenCost Helm values file:

   ```yaml
   serviceAccount:
     create: true
     annotations:
       eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/OpenCostRole
   ```

#### Access Key

`AWSAccessKey` authenticates with a long-lived IAM user access key. Create an Access Key for the OpenCost user who has access to the CUR: navigate to the [IAM Management Console dashboard](https://console.aws.amazon.com/iam), and select *Access Management > Users*. Find the OpenCost user and select *Security Credentials > Create Access Key*. Note the Access Key ID and Secret access key, then attach the [Cloud Costs IAM policy](#cloud-costs-iam-policy) to that user.

* `<ACCESS_KEY_ID>` is the ID of the Access Key created in the previous step.
* `<ACCESS_KEY_SECRET>` is the secret of the Access Key created in the previous step.

```json
{
  "aws": {
    "athena": [
      {
        "bucket": "<ATHENA_BUCKET_NAME>",
        "region": "<ATHENA_REGION>",
        "database": "<ATHENA_DATABASE>",
        "table": "<ATHENA_TABLE>",
        "workgroup": "<ATHENA_WORKGROUP>",
        "account": "<ACCOUNT_NUMBER>",
        "authorizer": {
          "authorizerType": "AWSAccessKey",
          "id": "<ACCESS_KEY_ID>",
          "secret": "<ACCESS_KEY_SECRET>"
        }
      }
    ]
  }
}
```

#### Assume Role

`AWSAssumeRole` wraps another authorizer and assumes a role from it, which is how you read a CUR that lives in a different AWS account than the cluster. Grant the wrapped identity `sts:AssumeRole` on `roleARN`, and attach the [Cloud Costs IAM policy](#cloud-costs-iam-policy) to the role being assumed:

```json
{
  "authorizerType": "AWSAssumeRole",
  "roleARN": "arn:aws:iam::123456789012:role/OpenCostRole",
  "authorizer": {
    "authorizerType": "AWSServiceAccount"
  }
}
```

#### Web Identity

`AWSWebIdentity` exchanges an OIDC identity token from outside AWS for AWS credentials. It is used when OpenCost runs on another cloud service provider and reads an AWS CUR:

```json
{
  "authorizerType": "AWSWebIdentity",
  "roleARN": "arn:aws:iam::123456789012:role/OpenCostRole",
  "identityProvider": "Google",
  "tokenRetriever": {
    "aud": "<AUDIENCE>"
  }
}
```

### Cloud Costs IAM policy

Whichever authorizer you choose, the resulting IAM identity needs to run Athena queries, read the table metadata from Glue, read and write the Athena query results bucket, and read the CUR bucket. Replace `<ATHENA_REGION>`, `<ACCOUNT_NUMBER>`, `<ATHENA_WORKGROUP>`, `<ATHENA_DATABASE>`, `<ATHENA_TABLE>`, `<ATHENA_BUCKET_NAME>` (the bucket name only, without the `s3://` prefix), and `<CUR_BUCKET_NAME>`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "Athena",
      "Effect": "Allow",
      "Action": [
        "athena:StartQueryExecution",
        "athena:GetQueryExecution",
        "athena:GetQueryResults",
        "athena:StopQueryExecution",
        "athena:GetWorkGroup"
      ],
      "Resource": "arn:aws:athena:<ATHENA_REGION>:<ACCOUNT_NUMBER>:workgroup/<ATHENA_WORKGROUP>"
    },
    {
      "Sid": "Glue",
      "Effect": "Allow",
      "Action": [
        "glue:GetDatabase",
        "glue:GetDatabases",
        "glue:GetTable",
        "glue:GetTables",
        "glue:GetPartitions"
      ],
      "Resource": [
        "arn:aws:glue:<ATHENA_REGION>:<ACCOUNT_NUMBER>:catalog",
        "arn:aws:glue:<ATHENA_REGION>:<ACCOUNT_NUMBER>:database/<ATHENA_DATABASE>",
        "arn:aws:glue:<ATHENA_REGION>:<ACCOUNT_NUMBER>:table/<ATHENA_DATABASE>/<ATHENA_TABLE>"
      ]
    },
    {
      "Sid": "QueryResultsBucket",
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation", "s3:ListBucket"],
      "Resource": "arn:aws:s3:::<ATHENA_BUCKET_NAME>"
    },
    {
      "Sid": "QueryResultsObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::<ATHENA_BUCKET_NAME>/*"
    },
    {
      "Sid": "CurBucket",
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation", "s3:ListBucket"],
      "Resource": "arn:aws:s3:::<CUR_BUCKET_NAME>"
    },
    {
      "Sid": "CurObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::<CUR_BUCKET_NAME>/*"
    }
  ]
}
```

The `Glue` statement covers the Athena metadata lookup OpenCost runs against `information_schema.columns` to discover which CUR columns exist. Without it, version detection fails and no Cloud Costs are returned.

### Verifying

Look for `AthenaIntegration[...]: GetCloudCost:` in the OpenCost logs, then check that `/model/cloudCost` returns non-empty data. If costs appear but nothing is attributed to Kubernetes, confirm that the `resource_tags` column is included in your CUR 2.0 export — excluding it silently drops OpenCost back to the CUR 1.0 code path.
